# Home categories + real Shorts sources — design

Date: 2026-11-08
Status: awaiting approval

## Intent

Two complaints from a real device run:

1. **The Shorts tab is not showing Shorts.** It currently searches Invidious for
   `#shorts`, filters by `lengthSeconds in 1..60`, and shows the result in a
   vertical pager. On the default instance that search returns only *landscape*
   clips (verified: 11/11 candidates were 1920×1080 or wider), so the pager is
   full of trailers, news cuts and horizontal "short films" with black bars.
2. **Home is one narrow feed.** `/api/v1/trending` returns 15 items and is the
   only source, so the screen feels static. The user wants category chips at
   the top (Movies, Games, Sports, News, …) and a much more varied feed.

Decision already taken with the user: option **A** for Shorts (dynamic channel
discovery + `/channels/{id}/shorts`) and option **A** for Home (chips that
replace the feed), with *more sources per category* to create the randomness.

## Goals

* Shorts tab contains only real vertical Shorts (9:16), mixed from several
  channels and reshuffled between reloads.
* Home has a horizontal chip row: `All · Music · Gaming · Movies · Sports ·
  News · Technology`.
* Every feed is built from several sources (trending + popular + several
  searches), deduplicated and shuffled; refresh produces a visibly different
  order/subset.
* A failing source degrades the feed instead of killing it.

## Non-goals

* No subscriptions, no personal recommendations, no watch-history ranking.
* No infinite scroll on Home (Invidious does not paginate trending/popular).
  Refresh remains the way to get new content.
* No server-side change; everything uses the existing Invidious instance.
* No offline caching of feeds (only the existing metadata write-through cache).
* No per-channel `/shorts` continuation paging: a channel's first page (48
  clips) is enough for one feed page, and channel rotation supplies variety.

## Constraints and facts verified against the instance

| Fact | Evidence |
|---|---|
| `search?q=#shorts&duration=short` returns only landscape clips | 11/11 candidates ≤60 s had `size` ≥ 1920×1080 |
| Invidious has no Shorts feed endpoint and ignores YouTube's Shorts shelf | search HTML contains no `/shorts/` links |
| `/api/v1/channels/{id}/shorts` returns real vertical Shorts | `size=144x256`, HLS `RESOLUTION=2160x3840`; 48 items on the first page |
| Shorts channels can be discovered dynamically | `search?type=channel&q=shorts` returns 20 channels (Shorts Break, A for Adley Shorts, Zakiiino, …) |
| `adaptiveFormats[].size` exposes real pixel dimensions | `"size": "256x144"` |
| Trending `type` is honoured only for Gaming on this instance | `Gaming` → 50 items; `Music/Movies/Sports/News` → the Default 15 |
| `/api/v1/popular` works and returns 40 items | direct call |
| Channel search payload fields | `authorId`, `author`, `authorThumbnails`, `subCount`, `description`, `autoGenerated`, `videoCount` |

## Approaches considered

### Shorts

* **A — dynamic channel discovery (chosen).** Search channels by several
  shorts-oriented queries, pick a few at random, fetch their `/shorts`, merge
  and shuffle. Guarantees vertical content without a hardcoded list.
  Trade-off: extra requests, content skews to shorts-compilation channels.
* **B — curated channel list.** Predictable but needs manual maintenance and
  gives a small, repetitive pool. Kept only as a resilience fallback.
* **C — keep search + filter by orientation via `adaptiveFormats[].size`.**
  Requires a details request per candidate and currently yields zero vertical
  results, so it cannot work on this instance.

### Home

* **A — chips that replace the feed (chosen).** Standard YouTube-like
  behaviour, simple state, one feed on screen.
* **B — category sections on one screen.** More requests, nested scrolling and
  a heavier UI for no clear benefit at this size.

## Design

### Domain (`:domain`)

```kotlin
enum class HomeCategory(val label: String) {
    ALL("All"),
    MUSIC("Music"),
    GAMING("Gaming"),
    MOVIES("Movies"),
    SPORTS("Sports"),
    NEWS("News"),
    TECHNOLOGY("Technology"),
}
```

`VideoRepository` gains:

```kotlin
suspend fun getHomeFeed(category: HomeCategory): List<Video>
```

`getTrending()` stays (it is a building block of `ALL`).

### Remote (`:data`)

`InvidiousService` additions:

```kotlin
@GET("api/v1/popular")
suspend fun getPopular(): List<VideoDto>

@GET("api/v1/channels/{channelId}/shorts")
suspend fun getChannelShorts(
    @Path("channelId") channelId: String,
    @Query("continuation") continuation: String? = null,
): ChannelVideosDto

@GET("api/v1/search")
suspend fun searchChannels(
    @Query("q") query: String,
    @Query("type") type: String = "channel",
    @Query("page") page: Int = 1,
): List<ChannelSearchDto>
```

New `ChannelSearchDto(authorId, author, authorThumbnails, subCount, description)`.

### Home feed algorithm (`VideoRepositoryImpl`)

A small internal model keeps the sources declarative:

```kotlin
private sealed interface FeedSource {
    data class Trending(val type: String) : FeedSource
    data object Popular : FeedSource
    data class Search(val query: String) : FeedSource
}
```

Per category:

| Category | Anchor sources | Search pool (2 picked at random for ALL, 3 for a topic) |
|---|---|---|
| ALL | trending Default, trending Gaming, popular | the union of all topic queries below |
| MUSIC | — | `music video`, `new song`, `official video`, `live music` |
| GAMING | trending Gaming | `gaming highlights`, `gameplay`, `esports highlights`, `new game` |
| MOVIES | — | `movie trailer`, `movie review`, `new movie`, `film trailer` |
| SPORTS | — | `sports highlights`, `football highlights`, `nba highlights`, `tennis highlights` |
| NEWS | — | `news today`, `world news`, `breaking news`, `daily news` |
| TECHNOLOGY | — | `technology review`, `tech news`, `gadgets`, `science technology` |

Music and Movies deliberately have **no** trending anchor: this instance
returns the generic Default feed for those `type` values, which would make the
chip indistinguishable from `All`. Only Gaming is verified to return a distinct
trending list, so it keeps that anchor.

Build steps:

1. Resolve the source list for the category; pick 2 search queries at random
   from its pool (`Random.Default`).
2. Fetch all sources **in parallel** (`coroutineScope` + `async`), each wrapped
   in `runCatching`; a failed source is skipped.
3. If every source failed, rethrow the first failure.
4. Map DTOs through the existing `toEntityOrNull()` (drops entries without
   `videoId`), deduplicate by id, shuffle, cap at `HOME_FEED_LIMIT = 60`.

Topic feeds therefore return ~40–60 items each; `ALL` returns the full mixed
pool. Refreshing re-picks queries and reshuffles, which is where the
"randomness" comes from.

### Shorts algorithm (`VideoRepositoryImpl`)

Constants:

```kotlin
private val SHORTS_CHANNEL_QUERIES = listOf(
    "shorts", "funny shorts", "dance shorts", "gaming shorts",
    "sports shorts", "movie shorts", "music shorts", "news shorts",
)
private val FALLBACK_SHORTS_CHANNELS = listOf(
    "UCgJ5_1F6yJhYLnyMszUdmUg", // Shorts Break
    "UCMHpfyAqrjrhn-mRS2bUL0g", // A for Adley Shorts
    "UCoi2zyVut5_hIKw4eEUji6g", // Zakiiino short
    "UCX6OQ3DkcsbYNE6H8uQQuVA", // MrBeast
)
private const val SHORTS_CHANNELS_PER_PAGE = 3
private const val SHORTS_PER_PAGE = 24
private const val SHORTS_MAX_SECONDS = 180L
```

`getShorts(page)`:

1. Pick 2 random channel queries; call `searchChannels` in parallel.
2. Collect unique `authorId`s, drop channels already used in this session,
   shuffle, take up to `SHORTS_CHANNELS_PER_PAGE`.
3. If the result is empty (discovery failed or all discovered channels were
   already used), reset the used set and pick from the fallback list plus the
   discovered list; this guarantees the feed can always continue.
4. Fetch each selected channel's `/shorts` in parallel; ignore individual
   failures.
5. Filter `lengthSeconds in 1L..SHORTS_MAX_SECONDS`, `!liveNow`, deduplicate.
6. Shuffle, take `SHORTS_PER_PAGE`, remember used channels (guarded by a
   `Mutex` because the repository is a singleton).
7. Return the list.

**Duration cap:** the app defines a Short as a vertical clip up to 3 minutes.
The channel endpoint only returns Shorts, so the old 60-second cap (which
silently dropped the 61–180 s Shorts YouTube has allowed since 2024) is raised.

**Seen clips and exhaustion:** the repository tracks *channels*, not video ids;
the ViewModel already deduplicates published clips. When a fetched page adds no
new ids, the ViewModel does **not** mark the feed as ended — it retries on the
next swipe (up to its attempt limit). It stops only when the repository returns
an empty list or the error state is shown.

**Empty vs failure contract:** if every selected channel request threw, the
repository rethrows the first failure (ViewModel shows an error with Retry). If
at least one channel succeeded but produced no usable clips, `getShorts`
returns an empty list.

Fallback search (`#shorts`) is **removed** for Shorts: it cannot produce
vertical clips on this instance.

### Home UI (`:app`)

`HomeScreen`:

* Keep the title row (`Home` + refresh button).
* Add a horizontally scrollable `LazyRow` of `FilterChip`s directly below it.
  Chips are driven by `HomeCategory.entries`, selection is highlighted.
* Feed area is unchanged: loading / error+retry / empty / list.

`HomeViewModel`:

* `selectedCategory: StateFlow<HomeCategory>` (default `ALL`).
* `selectCategory(category)` — switches and loads from an in-memory
  `Map<HomeCategory, List<Video>>` cache when available.
* `load()` / `refresh()` call `repository.getHomeFeed(selectedCategory)`;
  refresh bypasses and replaces the cache entry for the current category.
* Error/loading/refresh semantics stay as they are today.

### Shorts UI (`:app`)

* Add a small semi-transparent **refresh icon** in the top-right corner of the
  Shorts screen, wired to `ShortsViewModel.reload()`. Without it the pager is
  only created once per session (`saveState`/`restoreState`), so the "new mix"
  would never be visible in normal use.
* `reload()` that produces zero clips sets `UiState.Error("No shorts available
  right now")` (with the existing Retry behaviour) instead of an empty success,
  so the user is not stuck on a blank pager.
* `loadMore()` must not end the feed when a page yields only duplicates; it
  keeps the current list and retries on the next swipe until its attempt limit
  or an empty repository response.

### Tests

Repository (JVM, MockK):

* `ALL` merges trending + popular + search results, deduplicates and keeps a
  single copy of repeated ids.
* A failing source does not fail the feed (partial list returned).
* All sources failing → exception propagates.
* A topic category only calls its declared sources.
* Shorts: only 1..180 s items are kept, results are deduplicated, failing
  channels are skipped, discovery result is used (no legacy video search).
* Shorts: empty discovery falls back to the curated channel list.
* Shorts: channels already used are not requested again until the pool resets.
* Shorts: all selected channel requests failing → exception; one success with
  no usable clips → empty list.

ViewModel:

* Home starts on `ALL` and loads `getHomeFeed(ALL)`.
* Selecting a category loads it; selecting the same category again reuses the
  cache (no second repository call).
* Refresh re-fetches the current category.
* Errors/retry keep working.

A test shuffles the returned order, so assertions compare **sets** of ids, not
list order.

## Risks / trade-offs

* **More requests:** Home ≈ 4–6 calls, Shorts ≈ 4–6 calls per page, all in
  parallel. Per-category Home caching limits the visible cost.
* **Content quality:** dynamic discovery favours channels whose name/description
  mentions "shorts", often compilation channels. Acceptable for v1; the curated
  fallback and query pool can be extended later.
* **Instance fragility:** the instance occasionally returns 500 for a channel's
  shorts. The code treats it as an empty channel and continues.
* **No true vertical check:** we rely on `/channels/{id}/shorts` returning
  Shorts only. The API probe confirmed vertical dimensions; adding a details
  request per clip would triple the load.

* Exact wording/spacing of chips (Material 3 defaults).
* Whether to show a loading indicator per chip or a full-screen loader.
* Whether the `ALL` feed should include the topic searches always or only on
  refresh (default: include 2 random topic queries on every load).
